| D-60 | Límite de solicitudes para `POST /auth/refresh` y `POST /auth/logout`: 30 solicitudes por ventana de 15 minutos, por clave = IP + huella SHA-256 (16 hex) de la cookie `rt` (solo IP si no hay cookie). Respuesta 429 `RATE_LIMITED` con `Retry-After`. Valores configurables (`RATE_LIMIT_SESSION_MAX`, `RATE_LIMIT_SESSION_WINDOW_MINUTES`). Aclaración (B-04): cada operación lleva su propio contador (30 para refresh y 30 para logout, misma clave y misma ventana), para que un abuso de refresh no impida el logout, que es lo que revoca la sesión. `Retry-After` (segundos) y `details.minutes` salen del mismo cálculo: minutos restantes de la ventana, `ceil`, mínimo 1. Los contadores viven en memoria de un solo proceso. El login mantiene el límite del SDD (5 fallos / 15 min por IP + correo). | El contrato declara 429 en ambas operaciones pero el SDD no fijaba el límite. | D-62 | ETag débil según el contrato: `W/"<epoch ms de updatedAt>"` para todo recurso con `updatedAt` (hash débil del JSON solo si algún recurso no lo tuviera). `If-Match` es opcional; si viene se compara con el valor exacto del ETag actual, leído dentro de la misma transacción que escribe, y un desajuste responde 412 `PRECONDITION_FAILED` con `details.currentETag`. | D-63 | `DUPLICATE_NAME`: `<type>` es el sustantivo en minúsculas ("global variable") con el artículo correcto ("An application…"); `<application>` es el ámbito donde el nombre debe ser único: variable global, colección y pantalla → nombre de la aplicación; variable de contexto → nombre de su pantalla de origen; aplicación → "Documentación técnica". `details` conserva `{ field, type, name, application }` y agrega `container`: `application`, `screen` o `system`. Los nombres repetidos de componentes y de campos de colección vienen siempre del propio cuerpo (esos arrays se reemplazan completos): son 400 `VALIDATION_ERROR`, regla `unique`, campo `components[i].name` / `fields[i].name`, y no `DUPLICATE_NAME`. | El mensaje del catálogo no decía qué es `<application>` cuando la unicidad no es por aplicación (Tabla 31). | NFR-08 |
| D-64 | `CONTEXT_SCREEN_MISMATCH` (amplía la Tabla 59): con origen, `<variable> belongs to <pantalla de origen>. | D-65 | Errores de la base sin código propio en el catálogo → 400 `VALIDATION_ERROR` con `details.fields [{ field, rule: "CHECK" o "unique", message }]`, usando una tabla explícita constraint → campo (`src/http/dbRules.ts`), nunca inferencias por texto. Se aparta de la nota del SDD (23514 → 422) porque el catálogo define `VALIDATION_ERROR` como 400; los CHECK y triggers que sí tienen código siguen en 422 (SCOPE_MISMATCH, SCOPE_CONFLICT, CROSS_APPLICATION, APP_CONTEXT_PROTECTED, CONTEXT_SCREEN_MISMATCH). Vínculos y dependencias duplicados en un mismo PUT → 400 `unique` (el servicio valida antes con el índice exacto; la traducción de la base es el respaldo, sin índice). FK de dependencia inexistente (o de otro tipo) → 404 `NOT_FOUND`. `report_published_ready_chk` → 409 `REPORT_NOT_READY`. Borrar una fila referenciada (RESTRICT, SQLSTATE 23001/23503), los CHECK de combinaciones de dependencias (los tipos los deriva el servicio) y cualquier constraint que no esté en la tabla → 500 `INTERNAL_ERROR` registrado como error, porque la API nunca emite esos borrados ni esas combinaciones (sería un defecto). Duplicados de Jira (`jira_issue_id`, `jira_issue_key`, un Epic por pantalla) → 500 hasta el módulo de Jira, que hará upsert por `jira_issue_id` (TODO en `dbRules.ts`). | El SDD no define código para estos casos. | D-69 | Una variable `CONTEXT` SIN pantalla de origen no puede repetir nombre dentro de su aplicación: `409 DUPLICATE_NAME` con `container: application` y el nombre de la aplicación. La base no lo impide (el índice parcial `variable_context_name_key` no compara NULL), así que lo verifica el servicio dentro de la transacción de `POST` y `PUT`, protegido con `pg_advisory_xact_lock(VARIABLE_NAME_LOCK_SPACE, applicationId)` cuando el estado final es CONTEXT sin origen; la segunda de dos escrituras simultáneas ve la fila confirmada de la primera y responde 409. Sin migración nueva. `VARIABLE_NAME_LOCK_SPACE` es el espacio de locks (primer entero del par) reservado para este fin. | Sin la verificación, la misma variable sin origen podría registrarse varias veces. Un lock de aplicación solo serializa este caso, que es raro, y no requiere cambiar la base. | FR-05, FR-27 |
| D-70 | En un listado, `applicationId` inexistente o fuera del rango de `integer` → `404 NOT_FOUND` (`application`, es el recurso padre). | D-71 | Semántica de `PUT /variables/{id}`: `If-Match` se verifica SIEMPRE (también cuando el cuerpo no cambia nada), dentro de la transacción y sobre la fila bloqueada. Solo se escriben las columnas que cambian (así el trigger `check_context_screen_links`, que se dispara con `UPDATE OF scope, origin_screen_id`, no vuelve a juzgar una variable huérfana cuando solo se edita otro campo). Los ambientes se reemplazan por diferencia (insertar, actualizar notas, borrar) y, si cambian, también se actualiza `updated_at` de la variable. Un PUT que no cambia nada no escribe, no toca `updated_at`, no deja fila en `audit_log` y devuelve 200 con el mismo ETag. Orden de las reglas de negocio: `INVALID_ORIGIN_SCREEN` → `SCOPE_CONFLICT` → `CONTEXT_SCREEN_MISMATCH`. | Complementa D-62 y D-65; evita invalidar el ETag de otros editores sin que nada haya cambiado. | FR-05, FR-07, NFR-08 |
| D-72 | ETag de los GET (SDD Tabla 44, "Every GET returns an ETag"): los GET de un recurso con `updatedAt` envían el ETag de D-62 (`W/"<epoch ms>"`), que Express no reemplaza; los demás GET (listados, `dependencies`) envían el ETag débil por hash del cuerpo que Express genera por omisión (`app.set('etag')` sin cambiar). Un GET con `If-None-Match` que coincide responde `304` sin cuerpo. Comprobado con pruebas en `GET /variables/{id}`, `GET /variables` y `GET /variables/{id}/dependencies`. | Cumple la Tabla 44 sin código nuevo; desactivar el ETag automático la contradiría. El contrato debe declararlo (ver pendientes). | NFR-08, D-62 |
| D-73 | `overrides` acotado al paquete que trae la dependencia: `"@azure/identity": { "@azure/msal-node": "7.1.1" }` (versión exacta, como los demás). `@azure/identity` solo lo instala el CLI de Bruno (`@usebruno/cli` → `@usebruno/requests`). Se verifica con `npm run test:api`; si el CLI dejara de funcionar se revierte el override. | Deja `npm audit --audit-level=high` en 0 sin `--force` ni cambios en dependencias de producción. | NFR-17 |
| D-74 | Derivaciones de una colección (`derivedFrom`, dependencia `DERIVES_FROM`, D-29). Dirección: `source` = la colección editada, `target` = cada id de `derivedFrom` ("colActivos se construye desde colClientes"). `derivedFrom` no tiene id de fila: su clave natural es el par (origen, destino), así que se reconcilia por diferencia de conjunto (se inserta lo nuevo, se borra lo omitido, lo que sigue igual no se escribe y conserva su fila y su historia de auditoría). Una colección que se lista a sí misma → 400 `VALIDATION_ERROR` con `details.fields [{ field: "derivedFrom[i]", rule: "self", message: "A collection cannot derive from itself." }]`, verificado antes de abrir la transacción (por lo tanto antes de 404, 412 y 422); solo puede ocurrir en PUT. Los ciclos entre dos o más colecciones (A deriva de B y B de A) se **permiten**: el sistema documenta lo que existe, la base no los impide y `graph.sql` no es recursivo. Un `derivedFrom` repetido es 400 `unique` en `derivedFrom[i]`; una colección de origen inexistente es 404 con `field: "derivedFrom[i]"` y de otra aplicación 422 `CROSS_APPLICATION`. | El contrato no definía qué pasa con la autoderivación (la base la rechaza con `dependency_no_self_chk`, que sin esta decisión sería un 500) ni con los ciclos. | FR-09, FR-15 |
| D-75 | Ids anidados de un PUT de colección (`fields[i].id`, `variableAssignments[i].id`) que no pertenecen a esa colección (de otra colección, de otra aplicación o inexistentes, también fuera del rango de `integer`) → 404 `NOT_FOUND` con `details { element: "collection field" \| "variable assignment", id, field: "fields[2].id" }`. No es 400: así la respuesta no revela si el id existe en otra colección o aplicación, y coincide con D-65 (referencia inexistente → 404). | D-76 | Reglas 422 de las asignaciones (`variableAssignments`) de `POST` y `PUT /collections`: se aplican regla por regla y cada regla recorre el arreglo de arriba abajo; se informa el primer ítem que falla de la primera regla que falla. La primera es una referencia inválida y los datos de un elemento ajeno (scope, origen) no deben influir en el mensaje; `SET` con una variable CONTEXT ya es inválido por sí solo, y la tercera solo tiene sentido con `UPDATE_CONTEXT` sobre una variable CONTEXT. El scope sale de la base (`FOR SHARE`), nunca del cliente. Todo `details` lleva `field` con la posición: `CROSS_APPLICATION { field: "variableAssignments[i].variableId" \| ".screenId" \| "derivedFrom[i]" }`, `SCOPE_MISMATCH { field: "variableAssignments[i].assignmentFunction" }`, `CONTEXT_SCREEN_MISMATCH` con los details de D-64 (con y sin origen) más `field: "variableAssignments[i].screenId"`. Orden completo de errores de una escritura: 400 → 404 → 422 `APPLICATION_ARCHIVED` → 412 → 422 de negocio → 409 `DUPLICATE_NAME` (container `application`, D-63). Los triggers de la base quedan de respaldo (sin `field`). | Reglas deterministas y con posición para que la pantalla marque la fila. Criterio "manda la regla y no la posición" aprobado en B-09. | CP-07, D-52, FR-09 |

### Pendiente para la próxima versión del contrato (detectado en F-09)

- **`Screen.components[].uses` (y por tanto `GET /screens/{id}`).** El contrato declara el elemento de `uses` con `allOf` de `ComponentWrite` y del elemento de lectura, así que exige a la vez `targetId` (del esquema de escritura `ComponentUseWrite`) y `target` (objeto `Ref`). El API solo devuelve `{ id, targetType, target, description }`; no devuelve `targetId` (`repository.ts` del backend selecciona `target`). El tipo generado exige entonces un campo que el API nunca envía. En el frontend, `ScreenComponentsTab` lee solo `target` y convierte el tipo con un cast comentado (`as unknown as readonly Use[]`), y los datos de prueba incluyen `targetId` solo para satisfacer el tipo. Corrección propuesta para el contrato: declarar el elemento de lectura de `uses` por separado (sin `allOf` con `ComponentWrite`), o devolver también `targetId`; al cambiarlo, quitar el cast. Anotado también como pendiente en la descripción del PR de esta rama. No se modificó el backend ni el contrato.
