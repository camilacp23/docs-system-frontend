# Decisiones de la Fase 3 (posteriores al SDD v1.0)

Aprobadas por la autora el 18 de octubre de 2026. Deben incorporarse al SDD v1.1 (Tabla 70).

## Decisiones de diseño

| ID | Decisión | Justificación | Req. |
|---|---|---|---|
| D-60 | Límite de solicitudes para `POST /auth/refresh` y `POST /auth/logout`: 30 solicitudes por ventana de 15 minutos, por clave = IP + huella SHA-256 (16 hex) de la cookie `rt` (solo IP si no hay cookie). Respuesta 429 `RATE_LIMITED` con `Retry-After`. Valores configurables (`RATE_LIMIT_SESSION_MAX`, `RATE_LIMIT_SESSION_WINDOW_MINUTES`). Aclaración (B-04): cada operación lleva su propio contador (30 para refresh y 30 para logout, misma clave y misma ventana), para que un abuso de refresh no impida el logout, que es lo que revoca la sesión. `Retry-After` (segundos) y `details.minutes` salen del mismo cálculo: minutos restantes de la ventana, `ceil`, mínimo 1. Los contadores viven en memoria de un solo proceso. El login mantiene el límite del SDD (5 fallos / 15 min por IP + correo). | El contrato declara 429 en ambas operaciones pero el SDD no fijaba el límite. Una clave solo por IP bloquearía a todo un departamento detrás del mismo NAT. | NFR-05 |
| D-61 | `SessionResponse.data.sessionExpiresIn` (entero, segundos, obligatorio): segundos que faltan hasta el fin absoluto de la sesión de 12 h. Lo devuelven login y refresh. Contrato 0.3.0 → **0.3.1** (sin operaciones nuevas, sin cambios en la base). | El frontend necesita el fin de sesión para el aviso S-43a (10 min antes) y no puede leerlo de la cookie HttpOnly. Relativo en segundos, coherente con `expiresIn` e inmune al desfase del reloj del cliente. | NFR-01 |
| D-62 | ETag débil según el contrato: `W/"<epoch ms de updatedAt>"` para todo recurso con `updatedAt` (hash débil del JSON solo si algún recurso no lo tuviera). `If-Match` es opcional; si viene se compara con el valor exacto del ETag actual, leído dentro de la misma transacción que escribe, y un desajuste responde 412 `PRECONDITION_FAILED` con `details.currentETag`. Toda escritura de arrays anidados (componentes, vínculos, campos, asignaciones, entornos) debe actualizar también `updated_at` del recurso padre. Un id entero que no cabe en `integer` (> 2147483647) responde 404 `NOT_FOUND` sin llegar a Prisma; un id no numérico sigue siendo 400 del validador. | El contrato prevalece sobre una redacción distinta de la tarea (SDD §7). Sin actualizar el padre, dos editores verían el mismo ETag para documentos distintos. | NFR-08, D-24 |
| D-63 | `DUPLICATE_NAME`: `<type>` es el sustantivo en minúsculas ("global variable") con el artículo correcto ("An application…"); `<application>` es el ámbito donde el nombre debe ser único: variable global, colección y pantalla → nombre de la aplicación; variable de contexto → nombre de su pantalla de origen; aplicación → "Documentación técnica". `details` conserva `{ field, type, name, application }` y agrega `container`: `application`, `screen` o `system`. Los nombres repetidos de componentes y de campos de colección vienen siempre del propio cuerpo (esos arrays se reemplazan completos): son 400 `VALIDATION_ERROR`, regla `unique`, campo `components[i].name` / `fields[i].name`, y no `DUPLICATE_NAME`. | El mensaje del catálogo no decía qué es `<application>` cuando la unicidad no es por aplicación (Tabla 31). | NFR-08 |
| D-64 | `CONTEXT_SCREEN_MISMATCH` (amplía la Tabla 59): con origen, `<variable> belongs to <pantalla de origen>. From here you can only write it with Navigate.` y `details { variableId, variable, originScreenId, screen (origen), screenId (pantalla del vínculo), targetScreen }`. Variable de contexto SIN origen (mismo código y HTTP): `<variable> has no origin screen. Set its origin screen before linking it.` con `details { variableId, variable, originScreenId: null, screenId, targetScreen }`. El texto nuevo se agregará a la descripción del contrato en B-04, junto con 0.3.1. | El texto original sería falso cuando la variable no tiene pantalla de origen. El ejemplo del contrato mezclaba `screen` y `screenId`. | CP-07, D-52 |
| D-65 | Errores de la base sin código propio en el catálogo → 400 `VALIDATION_ERROR` con `details.fields [{ field, rule: "CHECK" o "unique", message }]`, usando una tabla explícita constraint → campo (`src/http/dbRules.ts`), nunca inferencias por texto. Se aparta de la nota del SDD (23514 → 422) porque el catálogo define `VALIDATION_ERROR` como 400; los CHECK y triggers que sí tienen código siguen en 422 (SCOPE_MISMATCH, SCOPE_CONFLICT, CROSS_APPLICATION, APP_CONTEXT_PROTECTED, CONTEXT_SCREEN_MISMATCH). Vínculos y dependencias duplicados en un mismo PUT → 400 `unique` (el servicio valida antes con el índice exacto; la traducción de la base es el respaldo, sin índice). FK de dependencia inexistente (o de otro tipo) → 404 `NOT_FOUND`. `report_published_ready_chk` → 409 `REPORT_NOT_READY`. Borrar una fila referenciada (RESTRICT, SQLSTATE 23001/23503), los CHECK de combinaciones de dependencias (los tipos los deriva el servicio) y cualquier constraint que no esté en la tabla → 500 `INTERNAL_ERROR` registrado como error, porque la API nunca emite esos borrados ni esas combinaciones (sería un defecto). Duplicados de Jira (`jira_issue_id`, `jira_issue_key`, un Epic por pantalla) → 500 hasta el módulo de Jira, que hará upsert por `jira_issue_id` (TODO en `dbRules.ts`). | El SDD no define código para estos casos. Una prueba falla si una migración nueva agrega un constraint sin entrada en la tabla. | NFR-08 |
| D-66 | Prisma 7.10.0 → **7.10.1** (`prisma`, `@prisma/client` y `@prisma/adapter-pg`, versiones exactas, subidas juntas). Sin cambios de esquema ni de migraciones (`npm run db:drift` sin diferencias). Regresión completa antes y después: lint, typecheck, build, 185 pruebas, 153 verificaciones heredadas, 219 comprobaciones de `test:api`, contrato válido y consistente con la base. El CI bloquea con `npm audit --omit=dev --audit-level=high` (0 vulnerabilidades tras la subida; antes 4 altas por deepmerge-ts y mysql2 dentro de Prisma). `npm audit` completo queda como paso informativo: sus 8 altas restantes son del CLI de Bruno 4.2.1 (solo desarrollo, sin corrección disponible; el arreglo que propone npm es bajar a 3.2.1). | Las vulnerabilidades altas de dependencias de producción no deben llegar a `main`; el parche 7.10.1 las corrige sin salir de la línea 7.10. | NFR-17 |

## Decisiones técnicas y de proceso (no cambian requisitos ni modelo)

| Tema | Decisión |
|---|---|
| Node | ≥ 22.22.0 (lo exigen react-router 8.4.0 y Vite 8.3.2). Sigue siendo Node 22 (SDD Tabla 7). |
| Lenguaje | TypeScript en backend (como la base) y frontend (`.tsx`, Figura 4). |
| Rutas frontend | Las planas de D-57 (la Figura 4 con `/apps/:appId` queda obsoleta). |
| Calidad | ESLint (typescript-eslint, `no-floating-promises` = R-1/D-20), Prettier, husky + lint-staged + commitlint (Conventional Commits). |
| Pruebas | Backend: `node:test` + supertest sobre bases desechables (rol `docs_app`). Frontend: Vitest + Testing Library. Las 153 verificaciones de la Fase 2 se conservan sin cambios como regresión. |
| Logging | `pino` + `pino-http`, JSON, `requestId` (también en `X-Request-Id` y en `INTERNAL_ERROR`), con redacción de `authorization`, `cookie`, `set-cookie`, `password`, `passwordHash`. |
| Siembra | `npm run db:seed` idempotente, ejecutado como `docs_app` (queda auditado con actor NULL y `db_role = docs_app`): primer administrador (`SEED_ADMIN_*`) y cuenta reservada "Integración Jira" (`INTEGRATION_USER_EMAIL`, READER, INACTIVE, hash inutilizable). No modifica cuentas existentes; si la reservada existe con datos distintos, falla. |
| Arranque | El API falla al arrancar si la cuenta reservada no existe o no es READER/INACTIVE (TODO_FASE3 #3). |
| Operaciones aún no implementadas | Pasan por autenticación, autorización y validación; responden 404 `NOT_FOUND` con `details.reason = "NOT_IMPLEMENTED"` y se listan en el log de arranque. Solo durante el desarrollo. |
| Ruta inexistente | 404 `NOT_FOUND` con `details.reason = "ROUTE_NOT_FOUND"`. |
| Detección de errores de la base | El adaptador `@prisma/adapter-pg` (Prisma 7.10) no expone el nombre del constraint en los CHECK ni en las excepciones de triggers, y los mensajes de PostgreSQL salen localizados. Prioridad: nombre de constraint (UNIQUE/FK) o SQLSTATE; nombre conocido dentro del mensaje (CHECK); texto literal del `RAISE` de los triggers del proyecto (cada uno con su prueba). `context_screen_mismatch` se detecta por el prefijo `CONTEXT_SCREEN_MISMATCH:` y el JSON de `detail` (TODO_FASE3 #4). Los mensajes de Prisma incluyen los argumentos de la consulta, así que nunca se escriben en el log. |
| Cadena de middlewares | El `requestId` y el log de acceso van justo después de CORS y antes de `express.json` (el SDD los lista después), para que un 400 o 413 del parser también lleve `X-Request-Id` y quede en el log. La validación de la solicitud se monta por operación, después de authenticate y authorize, para que 401 y 403 salgan antes que 400. Una operación con `x-roles` vacío que no sea login, refresh, logout o el webhook impide el arranque. El validador usa `allErrors`: `details.fields` lista todos los campos inválidos. |
| Desarrollo local | HTTP en `localhost`; frontend en `:5173` con proxy de Vite `/api` → `:3000`; `FRONTEND_ORIGIN=http://localhost:5173`. La cookie conserva `Secure` (Chrome/Edge la aceptan en localhost). HTTPS en el despliegue (NFR-04). |
| Contrato en el frontend | Copia en `contract/openapi.yaml` + `contract/SOURCE.md` (commit del backend), tipos con `openapi-typescript`, verificación en CI. |
| Fuentes | Plus Jakarta Sans e IBM Plex Mono autoalojadas (`@fontsource`), sin CDN. |
| Bruno | Versión 4.2.1; la colección la crea la autora en la app (formato nativo) dentro de `bruno/`; secretos en archivos ignorados. Se ejecuta contra una base aislada (`docs_sandbox`). |
| Git | `main` / `develop` / `feature/<nombre>`; Claude Code hace commits locales; push y PR los hace la autora. |
| CI | GitHub Actions en ambos repositorios. |
