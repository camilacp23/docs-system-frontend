| D-60 | Límite de solicitudes para `POST /auth/refresh` y `POST /auth/logout`: 30 solicitudes por ventana de 15 minutos, por clave = IP + huella SHA-256 (16 hex) de la cookie `rt` (solo IP si no hay cookie). Respuesta 429 `RATE_LIMITED` con `Retry-After`. Valores configurables (`RATE_LIMIT_SESSION_MAX`, `RATE_LIMIT_SESSION_WINDOW_MINUTES`). Aclaración (B-04): cada operación lleva su propio contador (30 para refresh y 30 para logout, misma clave y misma ventana), para que un abuso de refresh no impida el logout, que es lo que revoca la sesión. `Retry-After` (segundos) y `details.minutes` salen del mismo cálculo: minutos restantes de la ventana, `ceil`, mínimo 1. Los contadores viven en memoria de un solo proceso. El login mantiene el límite del SDD (5 fallos / 15 min por IP + correo). | El contrato declara 429 en ambas operaciones pero el SDD no fijaba el límite. | D-62 | ETag débil según el contrato: `W/"<epoch ms de updatedAt>"` para todo recurso con `updatedAt` (hash débil del JSON solo si algún recurso no lo tuviera). `If-Match` es opcional; si viene se compara con el valor exacto del ETag actual, leído dentro de la misma transacción que escribe, y un desajuste responde 412 `PRECONDITION_FAILED` con `details.currentETag`. Sin actualizar el padre, dos editores verían el mismo ETag para documentos distintos. | NFR-08, D-24 |
| D-63 | `DUPLICATE_NAME`: `<type>` es el sustantivo en minúsculas ("global variable") con el artículo correcto ("An application…"); `<application>` es el ámbito donde el nombre debe ser único: variable global, colección y pantalla → nombre de la aplicación; variable de contexto → nombre de su pantalla de origen; aplicación → "Documentación técnica". `details` conserva `{ field, type, name, application }` y agrega `container`: `application`, `screen` o `system`. Los nombres repetidos de componentes y de campos de colección vienen siempre del propio cuerpo (esos arrays se reemplazan completos): son 400 `VALIDATION_ERROR`, regla `unique`, campo `components[i].name` / `fields[i].name`, y no `DUPLICATE_NAME`. | El mensaje del catálogo no decía qué es `<application>` cuando la unicidad no es por aplicación (Tabla 31). | NFR-08 |

| D-65 | Errores de la base sin código propio en el catálogo → 400 `VALIDATION_ERROR` con `details.fields [{ field, rule: "CHECK" o "unique", message }]`, usando una tabla explícita constraint → campo (`src/http/dbRules.ts`), nunca inferencias por texto. Se aparta de la nota del SDD (23514 → 422) porque el catálogo define `VALIDATION_ERROR` como 400; los CHECK y triggers que sí tienen código siguen en 422 (SCOPE_MISMATCH, SCOPE_CONFLICT, CROSS_APPLICATION, APP_CONTEXT_PROTECTED, CONTEXT_SCREEN_MISMATCH). Vínculos y dependencias duplicados en un mismo PUT → 400 `unique` (el servicio valida antes con el índice exacto; la traducción de la base es el respaldo, sin índice). FK de dependencia inexistente (o de otro tipo) → 404 `NOT_FOUND`. `report_published_ready_chk` → 409 `REPORT_NOT_READY`. Borrar una fila referenciada (RESTRICT, SQLSTATE 23001/23503), los CHECK de combinaciones de dependencias (los tipos los deriva el servicio) y cualquier constraint que no esté en la tabla → 500 `INTERNAL_ERROR` registrado como error, porque la API nunca emite esos borrados ni esas combinaciones (sería un defecto). | D-69 | Una variable `CONTEXT` SIN pantalla de origen no puede repetir nombre dentro de su aplicación: `409 DUPLICATE_NAME` con `container: application` y el nombre de la aplicación. Sin migración nueva. `VARIABLE_NAME_LOCK_SPACE` es el espacio de locks (primer entero del par) reservado para este fin. | Sin la verificación, la misma variable sin origen podría registrarse varias veces. | D-71 | Semántica de `PUT /variables/{id}`: `If-Match` se verifica SIEMPRE (también cuando el cuerpo no cambia nada), dentro de la transacción y sobre la fila bloqueada. Solo se escriben las columnas que cambian (así el trigger `check_context_screen_links`, que se dispara con `UPDATE OF scope, origin_screen_id`, no vuelve a juzgar una variable huérfana cuando solo se edita otro campo). Los ambientes se reemplazan por diferencia (insertar, actualizar notas, borrar) y, si cambian, también se actualiza `updated_at` de la variable. Un PUT que no cambia nada no escribe, no toca `updated_at`, no deja fila en `audit_log` y devuelve 200 con el mismo ETag. Orden de las reglas de negocio: `INVALID_ORIGIN_SCREEN` → `SCOPE_CONFLICT` → `CONTEXT_SCREEN_MISMATCH`. | Complementa D-62 y D-65; evita invalidar el ETag de otros editores sin que nada haya cambiado. | FR-05, FR-07, NFR-08 |

| D-74 | Derivaciones de una colección (`derivedFrom`, dependencia `DERIVES_FROM`, D-29). | D-75 | Ids anidados de un PUT de colección (`fields[i].id`, `variableAssignments[i].id`) que no pertenecen a esa colección (de otra colección, de otra aplicación o inexistentes, también fuera del rango de `integer`) → 404 `NOT_FOUND` con `details { element: "collection field" \| "variable assignment", id, field: "fields[2].id" }`. | D-76 | Reglas 422 de las asignaciones (`variableAssignments`) de `POST` y `PUT /collections`: se aplican regla por regla y cada regla recorre el arreglo de arriba abajo; se informa el primer ítem que falla de la primera regla que falla.
